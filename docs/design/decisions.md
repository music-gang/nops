# Decision log

Design decisions in chronological order. A row is added **in the same commit**
that takes or changes a decision. The extended reasoning lives in
[philosophy](../philosophy.md) and the other documents.

A row is a decision and why, not an implementation diary: keep verification
notes, schemas and step-by-step "how it works" detail in the relevant
[design](.) or reference page, and link to it. When a later row replaces an
earlier one, mark the earlier row `(**Superseded by ...**)` rather than
leaving it silently wrong.

| 2026-09-23 | `hooks.Runner.Run` blocks until the hook reaches a terminal state and is idempotent: every step (row, dispatch, dispatched job ID, outcome) is persisted so calling it again resumes. A hook that fails or times out is a `Result`; only Nomad or SQLite failures are errors (the engine retries). | 2026-09-23 | Hook outcome: any `failed`/`lost` allocation → failed; success needs the dispatched job `dead` and every allocation `complete` (a multi-group hook with a group still pending is not a success); a completed allocation desired `stop` → failed (stopped from outside); no allocation yet → keep waiting until the timeout. | 2026-09-23 | Hook timeout: counted from `started_at`, checked after reading the outcome; on expiry `StopJob` (no purge) runs **before** `timed_out` is saved. Verified on Nomad 2.0.3: a finished batch allocation is `complete`/`run`, a stopped one `complete`/`stop`. |
| 2026-09-23 | A hook run is saved as `running` BEFORE `Dispatch` is sent (invariant 7), and the dispatched job ID right after. A resumed `running` run without a dispatched job ID is looked up by its idempotency token (`nomadx.FindDispatched`, using `DispatchIdempotencyToken` on the dispatched job) and adopted, so a crash or failed save after Nomad accepted the dispatch neither runs the hook twice nor leaves the dispatched job running past its timeout. If no dispatched job matches, the run is `failed` ("outcome unknown"), never dispatched again: it may have run and been garbage-collected, and then the token no longer deduplicates. The same applies to a saved dispatched job that has disappeared. Cost: a crash or a `Dispatch` error in the instant between the marker and Nomad receiving the request also fails the hook, loudly, instead of retrying it. The recovery fallback "look for children carrying `nops_deployment_id`" is replaced by the exact token match. |

| 2026-09-23 | Every secret also gets a second, env-only variable with the literal value (`NOPS_GIT_TOKEN` next to `NOPS_GIT_TOKEN_FILE`, and so on for every secret option: 8 then, 10 now that the OIDC client secret and the webhook secret exist), with no flag. | 2026-09-24 | The drift of a job under policy `none` is kept only in memory (`Engine.Observations()`), rebuilt from scratch on every detection cycle, not in a new table: it is always a function of the current git head and the current live job, so there is nothing that must survive a restart. | 2026-09-24 | A hook declared but missing from the repository (`nops_pre_hook`/`nops_post_hook` names no hook file in the current snapshot) fails the deployment at detection (`detected → failed`, with a notification), rather than waiting for an approval that is guaranteed to fail at the hook step. This is in addition to, not instead of, the runtime check `hooks.Runner` does again at dispatch time, since git can change in between. |
| 2026-09-24 | A new deployment is not created for a job whose latest one is `failed` or `rejected` with the same `spec_hash` and the same live index (`cas_index`): nothing that produced that outcome changed. A new commit or a change to the live job (a different index) creates a new deployment again, consistent with invariant 2 ("a CAS conflict leads to `failed` and a re-detection"). |
| 2026-09-24 | Revalidating an existing `detected`/`pending_approval` deployment (supersede on a spec change, on the live index changing, or completing an empty plan) compares `spec_hash`, never `commit_sha`: a commit that does not touch a job's file must not disturb its deployment. `spec_hash` itself is computed before task groups with a `scaling` block take their `Count` from the live job (Nops does not fight the autoscaler), so the autoscaler moving a count never supersedes a pending approval. |
| 2026-09-24 | Hook sync (register or update, plan + CAS) runs for every hook job found in the snapshot regardless of any one deployment's phase: a hook updated by a newer commit is synced immediately, even while an older deployment is still `pre_hook`/`post_hook` for the previous version. Hooks are already required to be idempotent; this adds tolerating a newer version of themselves being dispatched mid-deployment. (**Replaced by hook revisions, 2026-09-25**: there is no more per-cycle sync, see below.) |
| 2026-09-24 | `internal/engine`'s parse cache and in-memory observations are rebuilt from scratch and swapped in whole on every detection cycle, never mutated incrementally: a job or file no longer in the snapshot is dropped from both automatically, so neither grows over the life of the process. |
| 2026-09-24 | `pending_approval` is moved forward by `Engine.Approve`/`Reject`, not by `web` calling `Store.Transition` directly: `Approve` refuses if the caller's `spec_hash` no longer matches the deployment's current one (invariant 3), then picks `pre_hook` or `applying` by the same rule detection uses for `auto`. `web` only ever calls these two methods for a decision. |
| 2026-09-24 | `Store.SetApplied` persists `applied_index`/`eval_id` while a deployment stays `applying` (no schema change, guarded on `state = 'applying'`), because invariant 7 requires them saved before Nops waits for health and `Store.Transition` only writes on a state change. |
| 2026-09-24 | Apply health: a Nomad deployment for the applied job version reaching `successful`, or, when there is none (a `batch` job, or an `update` stanza that produces none), the allocations of that job version reaching `running` (or `complete`, which the code accepts for any job type, not only batch). `nomadx` gains a method to read a Nomad deployment by ID. |
| 2026-09-24 | The apply timeout counts from the `→ applying` event's timestamp (`Store.AppliedSince`, no schema change), not from a new column: the event is already written by `Transition` and already gives whole-second precision, same pattern as a hook's `started_at`. |
| 2026-09-24 | An apply that does not become healthy in time only gets `Transition` to `failed`: no `nomad deployment fail`, no automatic revert. Nops automates a manual GitOps process; what Nomad already does better (rolling update, canary, the job's own `auto_revert`) stays entirely Nomad's — Nops never steps in. |
| 2026-09-24 | A deployment that reached the register (`applied_index != 0`) and then `failed` blocks new deployments for the same job while the latest one keeps that `spec_hash`, whatever the live index is now (only a new commit, a different `spec_hash`, unblocks it). Without this, a job with `auto_revert` on loops forever: apply fails to become healthy, Nomad reverts it (changing the live index), the existing "same `spec_hash` and same `cas_index`" retry rule no longer matches the new index, and Nops re-applies the same rejected spec every cycle. This extends, not replaces, the existing retry rule for a failure that never reached the register. |
| 2026-09-24 | `Observation` gains `BlockedBy`/`BlockedReason`, filled by detection whenever a retry rule suppresses a new deployment for a job's drift, so a job stuck by either retry rule is visible in the dashboard instead of silently never converging. An explicit "retry without a new commit" dashboard action is deliberately left out for now: nothing in this design blocks adding one later, and it would be a thin wrapper over the same "create a deployment" path. |
| 2026-09-24 | Apply health (`engine-apply`) is decided from `nomadx.Client.LatestDeployment` (wraps `Jobs().LatestDeployment`, `nil` when the job has none) matched against `applied_index`, not from the register's `EvalID` and `Evaluations().Info` as first proposed: it needs no eval at all, which the crash-recovery register path does not always have, and adds no new `nomadx.Evaluation` wrapper. No match falls back to the allocations of the applied job version (`nomadx.Alloc` gains `JobVersion`), reusing the same failed/running/complete logic already used for hook outcomes. |
| 2026-09-24 | Workflow simplified after running `engine-apply` through it end to end. `plan first` no longer means a draft PR: the plan and open questions go to the maintainer in the session, before any branch exists, since the draft PR added a step (open it, push docs, wait) with no benefit over discussing it there directly, and its content (the design, the decisions) still ends up as a design page and decision-log rows once coding starts, same as before. A branch is no longer capped at one, amended commit either: with a single maintainer who squashes and edits the merge message by hand, keeping the branch to one commit added the overhead of `git commit --amend --force-with-lease` on every change for no reader who would otherwise see a messier history — a branch now carries as many commits as the work needs, each an honest step, and the maintainer turns them into `main`'s one commit at merge time. |
| 2026-09-24 | Recovery after a restart (`engine-recovery`) is the first cycle of `RunApply`, not a separate startup pass: `RunApply` already runs a cycle before its ticker, and every apply step resumes from the store alone, so no function is exported and no lock is added. It stays asynchronous (one goroutine per deployment) because a hook step blocks until its hook ends and a blocking pass would delay the dashboard and detection. Not chosen: a synchronous `Recover` before starting the loops (the same work, plus a startup that can hang for a hook's whole timeout). See [engine-apply](engine-apply.md), decision 8. |
| 2026-09-24 | Apply health fails a deployment when the live job's index is no longer `applied_index` and no Nomad deployment tracks that index ("job modified outside Nops while waiting for health"), instead of falling back to the allocations of the live version, which by then belong to someone else's spec. Found while writing the crash-window tests: a restart is the likeliest moment for an outside edit to slip in between the register and the health check. Not chosen: leave it as a known limitation, or a separate roadmap task for a few lines. |
| 2026-09-24 | The dashboard logs people in with built-in OpenID Connect (`coreos/go-oidc/v3`, `golang.org/x/oauth2`, `gorilla/securecookie`); `-auth-header` / `Remote-User` is gone. A header cannot be verified: anything that reaches Nops's port without going through the proxy (another allocation, the LAN, the tailnet) could approve a deployment by sending it, and a network mistake would fail silently. A signed ID token is checked by Nops itself, so a proxy in front is only for TLS. Not chosen: the trusted-proxies allowlist for the header (works, but the safety is still one firewall rule away from gone), Tailscale-only identity (ties Nops to one network). Costs: three dependencies, `-public-url` and the OIDC options become required, and Nops needs a client at the provider. See [dashboard](../dashboard.md#authentication). |
| 2026-09-24 | **Every** dashboard page needs a login, reads included, not only the writes: the plan diff says what runs on the cluster. Only `/auth/*`, the git webhook (its own secret) and the health check are open. |
| 2026-09-24 | The allowlist is required: `-oidc-allowed-users` (username or email) and/or `-oidc-allowed-groups` (the `groups` claim), and with both empty Nops does not start. Anyone who can authenticate at the provider would otherwise be able to approve a deployment, and a provider often serves more people than the cluster's operator. An email counts unless the provider says `email_verified: false`. The allowlist is checked at login only: a removal takes effect when the 12 hour session ends or Nops restarts. |
| 2026-09-24 | The session key is random at startup, not a configured secret: nothing to manage or leak, and the cost of a restart is one login, one redirect when the provider still has its session. Not chosen: `-session-key-file` (sessions surviving restarts, one more secret). |
| 2026-09-24 | OIDC discovery is lazy: Nops never contacts the provider at startup and retries it at every login (503 and an ERROR while it fails). A provider outage must not stop the engine, since `auto` deployments do not need a human. Not chosen: failing at startup (simpler, but an Authentik restart would also stop the deployments). |
