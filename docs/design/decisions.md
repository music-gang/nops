# Decision log

Design decisions in chronological order. A row is added **in the same commit**
that takes or changes a decision. The extended reasoning lives in
[philosophy](../philosophy.md) and the other documents.

| 2026-09-23 | State in SQLite (`modernc.org/sqlite`); per-job lock through a partial unique index. |

| 2026-09-23 | **pre_hook runs AFTER approval** (order changed from the initial spec): with migrations and backups nothing must run before the human OK. For pre-pulling the order does not change downtime. |
| 2026-09-23 | Apply = just a CAS register; the update is carried out by Nomad, no explicit stops. |
| 2026-09-23 | Active engine (not lazy). `pending_approval` deployments are revalidated on every cycle: index changed → `superseded` (+ a new deployment if there is drift); empty plan → `completed` no-op. No time-based expiry. |
| 2026-09-23 | Dashboard auth via the reverse proxy header (`Remote-User`); notifications via a generic webhook. |
| 2026-09-23 | Verified on `nomad agent -dev` 2.0.3: (1) `/v1/jobs/parse` rejects a `nops {}` block ("Unsupported block type"); (2) `Variables` works, with no value → "Unset variable"; (3) dispatch with undeclared meta → 500 "unpermitted metadata keys", with a missing required meta → 500; (4) `-idempotency-token` (API `IdempotencyToken`) returns the same dispatched job without a new evaluation, **even after the dispatched job has completed** (`dead`) → redispatching after a crash does not rerun the hook. |
| 2026-09-23 | Invalid meta (any ERROR) → policy `none` for the whole job, not just for the wrong key. |
| 2026-09-23 | Store: a single SQLite connection (serialized writes); `Transition` is the only way to change `state`, validates the transition table; `From` is required (compare-and-set on the state). |
| 2026-09-23 | Go module: `github.com/music-gang/nops`. |
| 2026-09-23 | CLAUDE.md holds only the working rules; all system documentation lives in `docs/`. |
| 2026-09-23 | Everything is written in English: code, comments, docs, examples, README, CLAUDE.md and commit messages. |
| 2026-09-23 | Commit messages follow the Angular convention (`type(scope): subject`). |
| 2026-09-23 | `nomadx` exposes only `RegisterCAS`: there is no register without the enforce-index check, so invariant 2 holds by construction. |
| 2026-09-23 | Verified on Nomad 2.0.3: every CAS failure is an HTTP 500 whose message starts with `Enforcing job modify index` (three variants: `job already exists`, `job exists with conflicting job modify index: N`, `job does not exist`), so `nomadx` recognises it by that prefix. A missing job is a real 404. The dispatch idempotency token travels as the `idempotency_token` query parameter (`WriteOptions.IdempotencyToken` in the Go client, not `DispatchOptions`). |
| 2026-09-23 | Registering a spec identical to the live one passes the CAS check and leaves the live `JobModifyIndex` unchanged, but the register response can carry a different index (raw HTTP: response 62, live 61). The engine re-reads the live job instead of trusting the response index. |
| 2026-09-23 | Workflow: pull requests into a protected `main` (ruleset: PR required, checks `test`/`lint`/`integration`/`pr-title`, up-to-date branch, linear history, no force push or deletion, no bypass). Squash merge only, so `main` is a straight line with one Angular-style commit per PR; the PR title is the commit subject. Zero required approvals because there is a single maintainer; CI is the gate. |
| 2026-09-23 | License: Apache-2.0, copyright holder Music Gang. Chosen for the explicit patent grant, inbound=outbound contributions and because it is the default of the Go/cloud-native ecosystem (and of nomad-gitops). All current dependencies (MPL-2.0, BSD-3, Apache-2.0) are compatible. |
| 2026-09-23 | Supply chain: GitHub Actions pinned to full SHAs (repository setting `sha_pinning_required`), read-only workflow token, workflows cannot approve PRs, Dependabot for Go modules and Actions. Nomad in CI is pinned to 2.0.3 with a SHA256 check. `govulncheck` is not a required check so a new advisory cannot block unrelated PRs. CodeQL default setup, secret scanning and push protection are on. |
| 2026-09-23 | `hooks.Runner.Run` blocks until the hook reaches a terminal state and is idempotent: every step (row, dispatch, dispatched job ID, outcome) is persisted so calling it again resumes. A hook that fails or times out is a `Result`; only Nomad or SQLite failures are errors (the engine retries). The `Request` carries the target job spec and commit rather than ready-made meta, so every hook misconfiguration (missing job, not a hook, not batch, unprovidable required meta, image collision) becomes one persisted `failed` in a single place. |
| 2026-09-23 | Hook outcome: any `failed`/`lost` allocation → failed; success needs the dispatched job `dead` and every allocation `complete` (a multi-group hook with a group still pending is not a success); a completed allocation desired `stop` → failed (stopped from outside); no allocation yet → keep waiting until the timeout. The failure message uses the task's `Terminated` (or driver/setup failure) event, not the last one: on Nomad 2.0.3 the last event is "Not Restarting: Policy allows no restarts", which hides the exit code. |
| 2026-09-23 | Hook timeout: counted from `started_at`, checked after reading the outcome; on expiry `StopJob` (no purge) runs **before** `timed_out` is saved. The decision only depends on persisted data and stopping is idempotent, so a crash between the two retries the stop; a stopped allocation seen past the deadline is read as our own stop (`timed_out`), not as an outside stop. Verified on Nomad 2.0.3: a finished batch allocation is `complete`/`run`, a stopped one `complete`/`stop`. |
| 2026-09-23 | A hook run is saved as `running` BEFORE `Dispatch` is sent (invariant 7), and the dispatched job ID right after. A resumed `running` run without a dispatched job ID is looked up by its idempotency token (`nomadx.FindDispatched`, using `DispatchIdempotencyToken` on the dispatched job) and adopted, so a crash or failed save after Nomad accepted the dispatch neither runs the hook twice nor leaves the dispatched job running past its timeout. If no dispatched job matches, the run is `failed` ("outcome unknown"), never dispatched again: it may have run and been garbage-collected, and then the token no longer deduplicates. The same applies to a saved dispatched job that has disappeared. Cost: a crash or a `Dispatch` error in the instant between the marker and Nomad receiving the request also fails the hook, loudly, instead of retrying it. The recovery fallback "look for children carrying `nops_deployment_id`" is replaced by the exact token match. |
| 2026-09-23 | Roadmap in one file, `docs/roadmap.md`, so a session that only has the repo (cloud, phone) knows what is done and what is next: no Issues or Projects, which would be a second ledger and are not always reachable. "In flight" is derived from the branch name (`type/<task-id>`), so there is nothing to keep in sync; "done" is set in the PR that finishes the task. Each task carries what to read, its dependencies and the notes that used to live in a private handoff note. A task with open design questions is `plan first`: a draft PR with the plan, no code, until the maintainer answers. |
| 2026-09-23 | Cloud sessions commit unsigned and open the PR; locally the maintainer keeps committing with GPG. Safe because the squash commit on `main` is created and signed by GitHub and the ruleset does not require signed commits; the branch commits are squashed away. A task given to a cloud session is the explicit request to commit, push and open a PR; never merging and never pushing to `main` stay. |
| 2026-09-23 | No PR template. The repository squashes with the PR description as the commit body (`PR_BODY`), copied verbatim, so the template's HTML comments, headings and checklist ended up on `main` (`a933a4c`, `8052989`; history cannot be rewritten). The PR description is written as a commit body instead, and the "done" checklist lives in `development.md`. Not chosen: `squash_merge_commit_message = COMMIT_MESSAGES` (body from the branch commits: untested with several commits) and cleaning the message by hand in the merge dialog. |
| 2026-09-23 | `docs/vocabulary.md` fixes the terms used in code, docs, commits and PRs. Bare "deployment" means the nops deployment; Nomad's is always "Nomad deployment". The hook's Nomad-side job is a "dispatched job" in docs (`child` stays acceptable in code for the parent/child link). A new or renamed concept updates the page in the same PR. |
| 2026-09-23 | Hook timeouts are rounded up to whole seconds (the store keeps `timeout_s`): `1500ms` → `2s`. Rounding down would time a hook out early; rejecting would add a failure path for a value `nops_*_hook_timeout` accepts. |
| 2026-09-23 | `nops_image_<task>` sanitizes the task name (non-alphanumeric → `_`); two tasks mapping to one key with different images make the hook `failed`. |
| 2026-09-23 | Configuration: every option has a flag and a `NOPS_<NAME>` variable, precedence flag > variable > default; an empty variable counts as unset. Every invalid value is reported at once, prefixed with its source. |
| 2026-09-23 | nops reads only its own flags and `NOPS_*` variables: the standard `NOMAD_*` variables are ignored and the Nomad client config is built field by field, not from `api.DefaultConfig()`. When nops runs as a Nomad job, Nomad sets `NOMAD_NAMESPACE`, `NOMAD_REGION` (and `NOMAD_TOKEN` with workload identity) in the task: with the defaults nops would silently work on its own namespace. It also keeps the naming uniform and every setting in one documented table. Verified in `nomad/api`: only `DefaultConfig` reads the environment; `NewClient` fills only an empty `Address` from it, and nops always sets one. |
| 2026-09-23 | Secrets are passed as file paths (`-git-token-file`, `-nomad-token-file`), read once at startup and trimmed, so they never appear in `ps` or in the job spec's `args`; as a Nomad job they come from a `template` (restart on change). Not chosen: env-only secrets (an exception to "every option has a flag") and token flags (visible in the command line). |
| 2026-09-23 | Git authentication: HTTPS token only (basic auth, `-git-username`, default `git`), which requires an `https://` URL. No SSH keys: a token covers GitHub, GitLab and Gitea with less to configure. |
| 2026-09-23 | Diff redaction (`internal/redact`) is a denylist on the names Nomad gives the diff fields, verified against a real Nomad 2.0.3 plan (kept as a test fixture and re-checked by an integration test): every `Env[...]` whatever its name, the template body `EmbeddedTmpl`, `GetterHeaders[...]`, every field below a check `Header`, `user:password@` in any URL, and any field or object name containing `password`, `token`, `secret`, `auth`, `credential`, `privatekey` or `apikey` (case-insensitive, `-` and `_` ignored). The last four words extend the list reused from nomad-gitops, so that `Authorization` and `X-Api-Key` headers are covered. Only the body of a template is redacted, not `DestPath` or `ChangeMode`, which carry no secret and help the reviewer. The value becomes `<redacted>` (empty stays empty) and the field name and change type stay. False positives (`Meta[author]`) are accepted over leaks; a secret inside a value under a harmless name (`args`) is a known limit, documented in dashboard.md. |
| 2026-09-23 | Notifications have built-in adapters: a generic JSON webhook, Discord, Slack, ntfy and Gotify. This replaces "Slack/Discord through an external adapter": the formats are a few lines each, and a self-hosted setup should not need n8n just to reach a chat. Each adapter has its own options (`-notify-<adapter>-url[-file]`, `-notify-<adapter>-token-file`) instead of a shared `url` + `kind` + `token`, so each is validated on its own without cross rules, and something specific to one adapter stays in its own options. An adapter is on when its URL is set, and several can be on at once. `-notify-url` is removed. |
| 2026-09-23 | Secrets in notifications: Discord and Slack webhook URLs carry their token, so they are files like every other secret; ntfy and Gotify take a plain server URL and a token file (required for Gotify). Neither the WARN of a failed delivery nor a config error ever contains a URL read from a file (`*url.Error` is unwrapped). |
| 2026-09-23 | A notification is sent synchronously, once per adapter, bounded by `-notify-timeout`, with no retry. A failure is a WARN and never reaches the engine; the other adapters still receive it. The engine calls it after the transition is saved and may run it in a goroutine. |
| 2026-09-23 | `-public-url` is the external URL of the dashboard (nops is behind a proxy and cannot know it). Notifications link to `<public-url>/deployments/<id>`; unset, they carry no link. |
| 2026-09-23 | Every secret also gets a second, env-only variable with the literal value (`NOPS_GIT_TOKEN` next to `NOPS_GIT_TOKEN_FILE`, and so on for all 8 secret options), with no flag. The earlier "secrets are files" rule was justified by `ps`/`/proc/<pid>/cmdline` exposure, which is real for a flag but not for an environment variable: a variable is only readable from `/proc/<pid>/environ`, by the same user or root, same exposure as a `0600` file. Forcing a file when the operator's own tool already injects a secret into the environment safely (systemd `EnvironmentFile`, `docker --env-file`, a Kubernetes `secretKeyRef`, a Nomad `template` with `env = true`) added friction with no security benefit. Precedence: flag file > variable file > this variable > off. Whether a literal secret ends up in a checked-in job's `env {}` block instead of Vault or a Nomad Variable stays the operator's call; nops cannot enforce that either way. |
| 2026-09-23 | The squash setting changes from "PR title and description" to "PR title and commit details" (`squash_merge_commit_message = COMMIT_MESSAGES`): the commit that lands on `main` is the branch's own single commit, in plain Angular style (no markdown headings — that is what `git log` shows), not the PR description. This is the common practice in projects that squash-merge and care about `git log` (Kubernetes and others): a clean commit for history, a separate, richer PR description for reviewers. The PR description is structured as `## What changes` / `## Why`, each a short bullet list, filled in by hand every time, with an optional `## Notes` for a maintainer decision or a note for the next task; this supersedes the earlier "no comments, headings or checklists" (that rule targeted a template's leftover HTML comments and unfilled checklist items landing on `main`, `a933a4c`/`8052989`, not deliberate, filled-in structure). It also corrects an earlier, mistaken reading of `squash_merge_commit_message = PR_BODY` as meaning the PR description was already copied verbatim onto `main`: in practice every squash so far (#8, #9, #10) was merged with the box cleared to the title alone, so nothing on `main` needs fixing — only the already-merged PR pages did, and were edited to drop the stray attribution lines. |
| 2026-09-23 | A commit or PR made by an assistant carries `Co-Authored-By` and nothing else attribution-wise: no session link or URL, no "Generated with ..." line. `Co-Authored-By` alone is enough to tell who or what wrote it; the rest holds no information for anyone reading `main` later. `docs/development.md#commit-messages` states this so it holds across sessions, regardless of a session's own default attribution instructions. |
| 2026-09-23 | gitwatch reads every `*.nomad.hcl` and `*.nomad` (the older `nomad job init` name) under an optional `-git-path` subdirectory, recursively. The vars file is `<name>.vars.hcl` next to the job file, `<name>` being the file name without `.nomad.hcl` / `.nomad`. Every other file is ignored silently, so a repo can also hold Terraform or Packer files. See [gitwatch](gitwatch.md). |
| 2026-09-23 | Whether a file is a managed job, a hook or neither is decided by its content after the Nomad parse (`nops_role = "hook"`, `nops_managed = "true"`), never by file name or directory: Nomad is the only HCL interpreter, and a naming rule could disagree with the content. A hook is looked up by its parsed job ID in the same snapshot; two files with the same job ID are both ignored, with an ERROR. |
| 2026-09-23 | A failed git fetch is an ERROR that keeps the last good snapshot and retries at the next tick, so detection (and Nomad-side drift) keeps running; `-git-path` missing in a new commit counts as a failed fetch, never as "every job removed". Only the initial clone is fatal. Each new head is a fresh shallow in-memory clone (after a cheap `ls-remote` shows a change), so memory stays constant and a force-push is just a new head. |
| 2026-09-23 | `internal/gitwatch` uses `github.com/go-git/go-git/v5` with `git.CloneContext(ctx, memory.NewStorage(), nil, ...)`: a nil worktree gives a bare, in-memory clone, so nothing ever touches disk and there is no checkout step to skip. `SingleBranch` + `Depth: 1` + `Tags: NoTags` keep each clone to the one commit needed. Tests run against a local bare repository over `file://`, which is how go-git's own test suite exercises the file transport; it shells out to the `git` binary (`git-upload-pack`), so the tests skip when `git` is not on `PATH`, an assumption already implied by the rest of the workflow (checking out this repository needs it too). |
| 2026-09-24 | `deployments.job_spec` keeps the full, unredacted parsed job: the database is local (same trust boundary as the HCL files and Nomad's own copy of the job), apply needs the exact spec that was planned and approved, and re-reading it from git at apply time does not work in general since gitwatch only keeps the current head. Mitigation: the database file, and its `-wal`/`-shm` sidecars, are created and kept at permission `0600` (`store.Open`); the dashboard never renders `job_spec`. See [engine-detection](engine-detection.md#job_spec-keeps-the-full-unredacted-spec). |
| 2026-09-24 | The drift of a job under policy `none` is kept only in memory (`Engine.Observations()`), rebuilt from scratch on every detection cycle, not in a new table: it is always a function of the current git head and the current live job, so there is nothing that must survive a restart. See [engine-detection](engine-detection.md#drift-of-a-none-policy-job-lives-only-in-memory). |
| 2026-09-24 | A hook declared but missing from the repository (`nops_pre_hook`/`nops_post_hook` names no hook file in the current snapshot) fails the deployment at detection (`detected → failed`, with a notification), rather than waiting for an approval that is guaranteed to fail at the hook step. This is in addition to, not instead of, the runtime check `hooks.Runner` does again at dispatch time, since git can change in between. |
| 2026-09-24 | A new deployment is not created for a job whose latest one is `failed` or `rejected` with the same `spec_hash` and the same live index (`cas_index`): nothing that produced that outcome changed. A new commit or a change to the live job (a different index) creates a new deployment again, consistent with invariant 2 ("a CAS conflict leads to `failed` and a re-detection"). |
| 2026-09-24 | Revalidating an existing `detected`/`pending_approval` deployment (supersede on a spec change, on the live index changing, or completing an empty plan) compares `spec_hash`, never `commit_sha`: a commit that does not touch a job's file must not disturb its deployment. `spec_hash` itself is computed before task groups with a `scaling` block take their `Count` from the live job (nops does not fight the autoscaler), so the autoscaler moving a count never supersedes a pending approval. |
| 2026-09-24 | Hook sync (register or update, plan + CAS) runs for every hook job found in the snapshot regardless of any one deployment's phase: a hook updated by a newer commit is synced immediately, even while an older deployment is still `pre_hook`/`post_hook` for the previous version. Hooks are already required to be idempotent; this adds tolerating a newer version of themselves being dispatched mid-deployment. |
| 2026-09-24 | `internal/engine`'s parse cache and in-memory observations are rebuilt from scratch and swapped in whole on every detection cycle, never mutated incrementally: a job or file no longer in the snapshot is dropped from both automatically, so neither grows over the life of the process. |
| 2026-09-24 | `pending_approval` is moved forward by `Engine.Approve`/`Reject`, not by `web` calling `Store.Transition` directly: `Approve` refuses if the caller's `spec_hash` no longer matches the deployment's current one (invariant 3), then picks `pre_hook` or `applying` by the same rule detection uses for `auto`. `web` only ever calls these two methods for a decision. |
| 2026-09-24 | `Store.SetApplied` persists `applied_index`/`eval_id` while a deployment stays `applying` (no schema change, guarded on `state = 'applying'`), because invariant 7 requires them saved before nops waits for health and `Store.Transition` only writes on a state change. |
| 2026-09-24 | Apply health: a Nomad deployment for the applied job version reaching `successful`, or, when there is none (a `batch` job, or an `update` stanza that produces none), the allocations of that job version reaching `running` (`running`/`complete` for a batch task group). `nomadx` gains a method to read a Nomad deployment by ID. |
| 2026-09-24 | The apply timeout counts from the `→ applying` event's timestamp (`Store.AppliedSince`, no schema change), not from a new column: the event is already written by `Transition` and already gives whole-second precision, same pattern as a hook's `started_at`. |
| 2026-09-24 | An apply that does not become healthy in time only gets `Transition` to `failed`: no `nomad deployment fail`, no automatic revert. nops automates a manual GitOps process; what Nomad already does better (rolling update, canary, the job's own `auto_revert`) stays entirely Nomad's — nops never steps in. |
| 2026-09-24 | A deployment that reached the register (`applied_index != 0`) and then `failed` blocks new deployments for the same job while the latest one keeps that `spec_hash`, whatever the live index is now (only a new commit, a different `spec_hash`, unblocks it). Without this, a job with `auto_revert` on loops forever: apply fails to become healthy, Nomad reverts it (changing the live index), the existing "same `spec_hash` and same `cas_index`" retry rule no longer matches the new index, and nops re-applies the same rejected spec every cycle. This extends, not replaces, the existing retry rule for a failure that never reached the register. |
| 2026-09-24 | `Observation` gains `BlockedBy`/`BlockedReason`, filled by detection whenever a retry rule suppresses a new deployment for a job's drift, so a job stuck by either retry rule is visible in the dashboard instead of silently never converging. An explicit "retry without a new commit" dashboard action is deliberately left out for now: nothing in this design blocks adding one later, and it would be a thin wrapper over the same "create a deployment" path. |
| 2026-09-24 | Apply health (`engine-apply`) is decided from `nomadx.Client.LatestDeployment` (wraps `Jobs().LatestDeployment`, `nil` when the job has none) matched against `applied_index`, not from the register's `EvalID` and `Evaluations().Info` as first proposed: it needs no eval at all, which the crash-recovery register path does not always have, and adds no new `nomadx.Evaluation` wrapper. No match falls back to the allocations of the applied job version (`nomadx.Alloc` gains `JobVersion`), reusing the same failed/running/complete logic already used for hook outcomes. |
| 2026-09-24 | Workflow simplified after running `engine-apply` through it end to end. `plan first` no longer means a draft PR: the plan and open questions go to the maintainer in the session, before any branch exists, since the draft PR added a step (open it, push docs, wait) with no benefit over discussing it there directly, and its content (the design, the decisions) still ends up as a design page and decision-log rows once coding starts, same as before. A branch is no longer capped at one, amended commit either: with a single maintainer who squashes and edits the merge message by hand, keeping the branch to one commit added the overhead of `git commit --amend --force-with-lease` on every change for no reader who would otherwise see a messier history — a branch now carries as many commits as the work needs, each an honest step, and the maintainer turns them into `main`'s one commit at merge time. |
