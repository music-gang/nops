# Decision log

Design decisions in chronological order. A row is added **in the same commit**
that takes or changes a decision. The extended reasoning lives in
[philosophy](../philosophy.md) and the other documents.

| Date | Decision |
|---|---|
| 2026-09-23 | Go, rewritten from scratch. Reused from nomad-gitops: parse via `/v1/jobs/parse`, plan-then-write, CAS register, supersede, diff redaction. |
| 2026-09-23 | State in SQLite (`modernc.org/sqlite`); per-job lock through a partial unique index. |
| 2026-09-23 | Policy and hooks as flat `nops_*` meta keys (custom blocks do not pass `/v1/jobs/parse`). |
| 2026-09-23 | Hook = a `parameterized` job in the repo, synced by nops; idempotent dispatch with token `<deployment_id>:<phase>`. |
| 2026-09-23 | **pre_hook runs AFTER approval** (order changed from the initial spec): with migrations and backups nothing must run before the human OK. For pre-pulling the order does not change downtime. |
| 2026-09-23 | Apply = just a CAS register; the update is carried out by Nomad, no explicit stops. |
| 2026-09-23 | Active engine (not lazy). `pending_approval` deployments are revalidated on every cycle: index changed → `superseded` (+ a new deployment if there is drift); empty plan → `completed` no-op. No time-based expiry. |
| 2026-09-23 | Dashboard auth via the reverse proxy header (`Remote-User`); notifications via a generic webhook. |
| 2026-09-23 | Verified on `nomad agent -dev` 2.0.3: (1) `/v1/jobs/parse` rejects a `nops {}` block ("Unsupported block type"); (2) `Variables` works, with no value → "Unset variable"; (3) dispatch with undeclared meta → 500 "unpermitted metadata keys", with a missing required meta → 500; (4) `-idempotency-token` (API `IdempotencyToken`) returns the same dispatched job without a new evaluation, **even after the dispatched job has completed** (`dead`) → redispatching after a crash does not rerun the hook. |
| 2026-09-23 | Invalid meta (any ERROR) → policy `none` for the whole job, not just for the wrong key. |
| 2026-09-23 | Store: a single SQLite connection (serialized writes); `Transition` is the only way to change `state`, validates the transition table; `From` is required (compare-and-set on the state). |
| 2026-09-23 | Go module: `github.com/music-gang/nops`. |
| 2026-09-23 | CLAUDE.md holds only the working rules; all system documentation lives in `docs/`. |
| 2026-09-23 | Everything is written in English: code, comments, docs, examples, README, CLAUDE.md and commit messages. |
| 2026-09-23 | Commit messages follow the Angular convention (`type(scope): subject`). |
| 2026-09-23 | `nomadx` exposes only `RegisterCAS`: there is no register without the enforce-index check, so invariant 2 holds by construction. |
| 2026-09-23 | Verified on Nomad 2.0.3: every CAS failure is an HTTP 500 whose message starts with `Enforcing job modify index` (three variants: `job already exists`, `job exists with conflicting job modify index: N`, `job does not exist`), so `nomadx` recognises it by that prefix. A missing job is a real 404. The dispatch idempotency token travels as the `idempotency_token` query parameter (`WriteOptions.IdempotencyToken` in the Go client, not `DispatchOptions`). |
| 2026-09-23 | Registering a spec identical to the live one passes the CAS check and leaves the live `JobModifyIndex` unchanged, but the register response can carry a different index (raw HTTP: response 62, live 61). The engine re-reads the live job instead of trusting the response index. |
| 2026-09-23 | Workflow: pull requests into a protected `main` (ruleset: PR required, checks `test`/`lint`/`integration`/`pr-title`, up-to-date branch, linear history, no force push or deletion, no bypass). Squash merge only, so `main` is a straight line with one Angular-style commit per PR; the PR title is the commit subject. Zero required approvals because there is a single maintainer; CI is the gate. |
| 2026-09-23 | License: Apache-2.0, copyright holder Music Gang. Chosen for the explicit patent grant, inbound=outbound contributions and because it is the default of the Go/cloud-native ecosystem (and of nomad-gitops). All current dependencies (MPL-2.0, BSD-3, Apache-2.0) are compatible. |
| 2026-09-23 | Supply chain: GitHub Actions pinned to full SHAs (repository setting `sha_pinning_required`), read-only workflow token, workflows cannot approve PRs, Dependabot for Go modules and Actions. Nomad in CI is pinned to 2.0.3 with a SHA256 check. `govulncheck` is not a required check so a new advisory cannot block unrelated PRs. CodeQL default setup, secret scanning and push protection are on. |
| 2026-09-23 | `hooks.Runner.Run` blocks until the hook reaches a terminal state and is idempotent: every step (row, dispatch, dispatched job ID, outcome) is persisted so calling it again resumes. A hook that fails or times out is a `Result`; only Nomad or SQLite failures are errors (the engine retries). The `Request` carries the target job spec and commit rather than ready-made meta, so every hook misconfiguration (missing job, not a hook, not batch, unprovidable required meta, image collision) becomes one persisted `failed` in a single place. |
| 2026-09-23 | Hook outcome: any `failed`/`lost` allocation → failed; success needs the dispatched job `dead` and every allocation `complete` (a multi-group hook with a group still pending is not a success); a completed allocation desired `stop` → failed (stopped from outside); no allocation yet → keep waiting until the timeout. The failure message uses the task's `Terminated` (or driver/setup failure) event, not the last one: on Nomad 2.0.3 the last event is "Not Restarting: Policy allows no restarts", which hides the exit code. |
| 2026-09-23 | Hook timeout: counted from `started_at`, checked after reading the outcome; on expiry `StopJob` (no purge) runs **before** `timed_out` is saved. The decision only depends on persisted data and stopping is idempotent, so a crash between the two retries the stop; a stopped allocation seen past the deadline is read as our own stop (`timed_out`), not as an outside stop. Verified on Nomad 2.0.3: a finished batch allocation is `complete`/`run`, a stopped one `complete`/`stop`. |
| 2026-09-23 | A hook run is saved as `running` BEFORE `Dispatch` is sent (invariant 7), and the dispatched job ID right after. A resumed `running` run without a dispatched job ID is looked up by its idempotency token (`nomadx.FindDispatched`, using `DispatchIdempotencyToken` on the dispatched job) and adopted, so a crash or failed save after Nomad accepted the dispatch neither runs the hook twice nor leaves the dispatched job running past its timeout. If no dispatched job matches, the run is `failed` ("outcome unknown"), never dispatched again: it may have run and been garbage-collected, and then the token no longer deduplicates. The same applies to a saved dispatched job that has disappeared. Cost: a crash or a `Dispatch` error in the instant between the marker and Nomad receiving the request also fails the hook, loudly, instead of retrying it. The recovery fallback "look for children carrying `nops_deployment_id`" is replaced by the exact token match. |
| 2026-09-23 | Roadmap in one file, `docs/roadmap.md`, so a session that only has the repo (cloud, phone) knows what is done and what is next: no Issues or Projects, which would be a second ledger and are not always reachable. "In flight" is derived from the branch name (`type/<task-id>`), so there is nothing to keep in sync; "done" is set in the PR that finishes the task. Each task carries what to read, its dependencies and the notes that used to live in a private handoff note. A task with open design questions is `plan first`: a draft PR with the plan, no code, until the maintainer answers. |
| 2026-09-23 | Cloud sessions commit unsigned and open the PR; locally the maintainer keeps committing with GPG. Safe because the squash commit on `main` is created and signed by GitHub and the ruleset does not require signed commits; the branch commits are squashed away. A task given to a cloud session is the explicit request to commit, push and open a PR; never merging and never pushing to `main` stay. |
| 2026-09-23 | No PR template. The repository squashes with the PR description as the commit body (`PR_BODY`), copied verbatim, so the template's HTML comments, headings and checklist ended up on `main` (`a933a4c`, `8052989`; history cannot be rewritten). The PR description is written as a commit body instead, and the "done" checklist lives in `development.md`. Not chosen: `squash_merge_commit_message = COMMIT_MESSAGES` (body from the branch commits: untested with several commits) and cleaning the message by hand in the merge dialog. |
| 2026-09-23 | `docs/vocabulary.md` fixes the terms used in code, docs, commits and PRs. Bare "deployment" means the nops deployment; Nomad's is always "Nomad deployment". The hook's Nomad-side job is a "dispatched job" in docs (`child` stays acceptable in code for the parent/child link). A new or renamed concept updates the page in the same PR. |
| 2026-09-23 | Hook timeouts are rounded up to whole seconds (the store keeps `timeout_s`): `1500ms` → `2s`. Rounding down would time a hook out early; rejecting would add a failure path for a value `nops_*_hook_timeout` accepts. |
| 2026-09-23 | `nops_image_<task>` sanitizes the task name (non-alphanumeric → `_`); two tasks mapping to one key with different images make the hook `failed`. |
| 2026-09-23 | Configuration: every option has a flag and a `NOPS_<NAME>` variable, precedence flag > variable > default; an empty variable counts as unset. Every invalid value is reported at once, prefixed with its source. |
| 2026-09-23 | nops reads only its own flags and `NOPS_*` variables: the standard `NOMAD_*` variables are ignored and the Nomad client config is built field by field, not from `api.DefaultConfig()`. When nops runs as a Nomad job, Nomad sets `NOMAD_NAMESPACE`, `NOMAD_REGION` (and `NOMAD_TOKEN` with workload identity) in the task: with the defaults nops would silently work on its own namespace. It also keeps the naming uniform and every setting in one documented table. Verified in `nomad/api`: only `DefaultConfig` reads the environment; `NewClient` fills only an empty `Address` from it, and nops always sets one. |
| 2026-09-23 | Secrets are passed as file paths (`-git-token-file`, `-nomad-token-file`), read once at startup and trimmed, so they never appear in `ps` or in the job spec's `args`; as a Nomad job they come from a `template` (restart on change). Not chosen: env-only secrets (an exception to "every option has a flag") and token flags (visible in the command line). |
| 2026-09-23 | Git authentication: HTTPS token only (basic auth, `-git-username`, default `git`), which requires an `https://` URL. No SSH keys: a token covers GitHub, GitLab and Gitea with less to configure. |
| 2026-09-23 | Diff redaction (`internal/redact`) is a denylist on the names Nomad gives the diff fields, verified against a real Nomad 2.0.3 plan (kept as a test fixture and re-checked by an integration test): every `Env[...]` whatever its name, the template body `EmbeddedTmpl`, `GetterHeaders[...]`, every field below a check `Header`, `user:password@` in any URL, and any field or object name containing `password`, `token`, `secret`, `auth`, `credential`, `privatekey` or `apikey` (case-insensitive, `-` and `_` ignored). The last four words extend the list reused from nomad-gitops, so that `Authorization` and `X-Api-Key` headers are covered. Only the body of a template is redacted, not `DestPath` or `ChangeMode`, which carry no secret and help the reviewer. The value becomes `<redacted>` (empty stays empty) and the field name and change type stay. False positives (`Meta[author]`) are accepted over leaks; a secret inside a value under a harmless name (`args`) is a known limit, documented in dashboard.md. |
